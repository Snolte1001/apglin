# Audi 8W1 919 616: Bedienteil Radio am LIN-Bus

Dreh-Drück-Knopf mit Kippfunktion links/rechts und Tastenbeleuchtung.
Belegung am 30.10.2026 an
einem Gerät gemessen: APGDT001 (Firmware `0x2304`) als Master mit
Master-Pull-up, VBAT, Bedienteil als einziger Slave. Der Analyzer hat ID
`0x10` etwa alle 30 ms abgefragt (31 318 Frames, ohne Fehler außer den
Weck-Headern), dabei wurde jede Funktion einzeln und in Kombination bedient.

Mitschnitt: [`tests/recordings/audi_8w1919616_frames.txt`](../tests/recordings/audi_8w1919616_frames.txt),
Tests: `tests/test_audi_8w1919616.py`, Beispiel mit Decoder und
Abfrageschleife: [`examples/audi_8w1919616.py`](../examples/audi_8w1919616.py),
LDF (LIN 2.1): [`AUDI_8W1919616.ldf`](AUDI_8W1919616.ldf).

Die LDF ist aus diesen Messungen rekonstruiert, nicht von Audi; Signalnamen
sind frei gewählt. Gemessen sind Baudrate, IDs, Längen, Prüfsummen,
Signallage, Response_Error, NAD und Product ID. Diagnose-Zeiten
(P2_min, ST_min, N_As/N_Cr), Zeitbasis, Zykluszeiten und Startwerte sind
LIN-2.1-Standardwerte bzw. Annahmen. `tests/test_audi_ldf.py` prüft die
LDF mit `ldfparser` gegen den Decoder und alle mitgeschnittenen Frames.

## Bus

| | |
|---|---|
| Baudrate | 19200 Bd (bei 9600 und 10417 Bd keine Antwort) |
| Frame | ID `0x10` (PID `0x50`), Slave-Antwort, 2 Datenbytes |
| Prüfsumme | enhanced (Ruhe: `00 00`, Prüfsumme `AF`) |
| andere IDs | keine Antwort auf `0x00`–`0x3F` außer `0x10` |
| Schlaf | nach etwa 4–5 s ohne Header beantwortet das Bedienteil den ersten Header nicht (Aufwachen), erst den nächsten |
| unaufgefordert | sendet nichts von sich aus, nur auf Header |
| Master-Frame | ID `0x01` (PID `0xC1`), 1 Datenbyte, enhanced: Tastenbeleuchtung, siehe unten |

Ohne den Frame `0x01` antwortet das Bedienteil ebenso. Beim Senden an alle
IDs `0x00`–`0x3B` (1–8 Byte `00`, `FF`, `64`, `7F`) schaltete nur `0x01`
das Licht; `00` an alle IDs außer `0x01` ließ es an. Ob andere IDs etwas
anderes bewirken, ist nicht untersucht, ebenso die Diagnose-IDs
`0x3C`/`0x3D` (nicht gesendet, um die Konfiguration nicht zu verändern).

Die Frame-IDs folgen nicht dem Längenschema von LIN 1.3 (`0x01` hat 1 Byte),
und die Prüfsummen sind enhanced. Dazu passt das Response_Error-Bit: Das
Bedienteil arbeitet nach LIN 2.x.

## Datenbytes

| Byte | Bits | Bedeutung |
|---|---|---|
| 0 | ganzes Byte, vorzeichenbehaftet | Drehung seit der letzten Abfrage: `01` = eine Raste rechts, `FF` = eine Raste links |
| 1 | Bit 0 (`01`) | gedrückt |
| 1 | Bit 1 (`02`) | nie gesehen |
| 1 | Bit 2 (`04`) | links gekippt |
| 1 | Bit 3 (`08`) | rechts gekippt |
| 1 | Bit 4 (`10`) | Response_Error (LIN 2.x): einen fehlerhaften Frame an `0x01` empfangen, siehe unten |
| 1 | Bit 5–7 | nie gesehen |

- Drehung: Jede Raste erscheint in genau einem Frame, danach wieder `00`.
  Auch bei schnellem Drehen stand nie mehr als ±1 in einem Frame, zwischen
  zwei Rasten lag immer mindestens ein Frame mit `00` (kürzester Abstand
  etwa 56 ms). Ob bei noch schnellerem Drehen Rasten verloren gehen oder
  nur verzögert gemeldet werden, ist nicht geprüft (Rastenzahl nicht
  gezählt).
- Tasten: Das Bit steht, solange die Taste gehalten wird. Langes Drücken
  hat keinen eigenen Code (3,3 s gehalten: durchgehend `01`).
- Kombinationen: Alle Funktionen sind unabhängig. Gedrückt und gekippt
  ergibt `09` bzw. `05`, gedrückt und gedreht `FF 01` bzw. `01 01`.

Beispiele:

| Frame | Bedeutung |
|---|---|
| `00 00` | Ruhe |
| `FF 00` | eine Raste links |
| `01 00` | eine Raste rechts |
| `00 01` | gedrückt |
| `00 04` | links gekippt |
| `00 08` | rechts gekippt |
| `00 09` | gedrückt und rechts gekippt |
| `FF 01` | gedrückt und eine Raste links |

## Tastenbeleuchtung (ID `0x01`)

Der Master sendet ID `0x01` mit einem Datenbyte, die Helligkeit in Prozent.
Am Gerät mit bloßem Auge beobachtet (30.10.2026):

| Wert | Beobachtung |
|---|---|
| `00` | aus |
| `01` | sehr dunkel (im Wechsel mit `00` sichtbar) |
| `0A` | dunkel |
| `32` | sichtbar dunkler als `FF` (Wechsel im Sekundentakt pulsiert) |
| `64` | voll; im Wechsel mit `FF` kein Unterschied |
| `80`, `FF` | voll |

- Das Bedienteil behält den zuletzt empfangenen Wert. Das Licht bleibt an,
  wenn danach keine Frames mehr kommen, auch wenn das Bedienteil nach 4 s
  Busruhe in den Schlafmodus geht (20 s geprüft).
- Nur Frames mit genau 1 Byte und enhanced-Prüfsumme wirken. 2–8 Byte,
  falsche oder classic-Prüfsumme werden verworfen.
- Verworfene Frames meldet das Bedienteil über Bit 4 in Byte 1 seiner
  Antwort auf `0x10` (Response_Error): Es steht in genau einer Antwort und
  ist danach gelöscht. Ein Header `0x01` ohne Daten zählt nicht als Fehler.
  Mitschnitt: `tests/recordings/slave_audi_illumination.txt`.

```python
lin.send_frame(0x01, bytes([100]), ChecksumType.ENHANCED)   # voll
lin.send_frame(0x01, bytes([0]), ChecksumType.ENHANCED)     # aus
```

Gefunden durch Senden an alle IDs (Licht sprang an), Ausschalten mit `00`
und anschließendes Halbieren der Längen.

## Diagnose

Nur lesend geprüft: Read by Identifier (SID `B2`) an die Wildcard-NAD `7F`.

| Anfrage `0x3C` (classic) | Antwort `0x3D` | Bedeutung |
|---|---|---|
| `7F 06 B2 00 FF 7F FF FF` | `40 06 F2 49 00 01 30 00` | NAD `0x40`, Supplier ID `0x0049`, Function ID `0x3001`, Variant `0x00` |
| `7F 06 B2 01 FF 7F FF FF` | `40 03 7F B2 12 FF FF FF` | Seriennummer nicht unterstützt (negative Antwort, NRC `12`) |

Konfigurierende Dienste (Assign NAD, Assign Frame ID usw.) wurden nicht
gesendet.

## Abfragen

Header nur senden, wenn der vorige ausgeführt und beantwortet ist, und
verpasste Abfragen nicht nachholen: Zwei Header direkt hintereinander
zerstören die Antwort (siehe PROTOKOLL.md, „Fremder Slave“).

```python
lin.send_header(0x10, wait=True)
time.sleep(0.02)
```
